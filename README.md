# probe-harness-krafton

> **이 키트는 공개 레포 반입이 허용된 시험에서만 세팅한다.** 허용이 명시되지 않았으면 시작 전에 응시 규정 화면·문의로 확인한다. 확인 전에는 클론도 `setup.sh` 도 돌리지 않는다.

Cofa Probe 형 AI 협업 시험(원격 리눅스 데스크톱 · 제공 Codex 앱 · Chromium) 응시자가 쓰는 범용 작업 하네스. 실무자와 DM 으로 문제를 확정하고, 풀이를 만들고, 풀이 뒤 후속 서술형(AI 금지)에 답하는 시험을 가정한다. 회사·대회에 묶인 내용은 넣지 않았다 — 그 시험의 값(제출물 · 시간 · 금지)은 세팅 뒤 `docs/과제설정.md` 한 곳에 적는다.

## 이 README 를 읽은 에이전트에게 — 지금 상황

- 사용자는 지금 **시험 중**이다. 과제 타이머가 시작됐고 과제 풀이 뒤 후속 서술형(AI 금지)이 있다. 실제 시작·종료 시각은 세팅 뒤 `docs/과제설정.md` 4절에 적는다.
- **너는 오케스트레이터(오케)다.** 계획·분해·공유 문서·검수·커밋을 맡고, **사용자와 논의하며 진행한다**. 실무자 대화는 DM 세션이, 사용자의 서술형 대비는 설명 세션이 처음부터 돕는다. 구현·서버·E2E 는 처음엔 오케 하나로 가고, 일이 커지면 오케가 구현·통합·검증 세션(탭)이나 서브에이전트를 쓰자고 **제안**해 사용자가 승인하면 늘린다 — 스스로 늘리지 않는다. 탭 수 상한은 시험마다 다르다(`harness/guides/편성.md`).
- 작업 공간(사용자가 Codex 를 연 폴더) 루트의 `README.md` 와 그 옆 파일들(출력 계약 · 데이터 설명 · 제출 양식)은 **과제 원문**이다. 이 레포의 README(지금 이 글)와 다르다. 세팅은 과제 원문을 덮지 않는다.
- 공통 규칙은 세팅 뒤 작업 공간에 생기는 `AGENTS.md`, 오케의 신호 규칙은 `harness/roles/오케.md` 다.
- 이 환경에서 파일 업로드와 Skill 등록 UI 는 막혀 있다. 스킬은 작업 공간 안 `.agents/skills/` 로만 쓴다. Codex 에서 이미지 생성은 된다(화면 목업 · 발표 도판 — 사용 한도를 빨리 쓰니 꼭 필요한 목업·도판만).
- **Codex 는 터미널 CLI 가 아니라 앱일 수 있다.** 키트 문서는 CLI(탭마다 `codex`, `codex queue`)를 전제로 쓰였으니 세팅 직후 실측 4가지로 작업 방식 A(터미널 CLI) / B(앱 chat)를 판정해 `docs/과제설정.md` 7절에 적는다 — B 이면 탭 = 사이드바 chat, 세션 간 전달 = 파일 우편함(`AGENTS.md` 「세션 등록」). 사람용 조작 안내는 루트 `Codex-앱-조작.md`.

## 세팅 — 이 레포를 클론하라는 요청을 받았으면 (사용자 문구가 「상황 파악」「세팅」 등 무엇이든 같다)

1. 클론 위치는 **작업 공간 안의 `probe-harness-krafton/`** 다. 다른 곳에 클론했으면 아래 명령에 작업 공간 경로를 인자로 넘긴다.
2. 작업 공간에서 실행한다:
   ```bash
   bash probe-harness-krafton/setup.sh
   ```
   setup.sh 는 **고치지 않고 그대로** 돌린다. **이 스크립트는 작업 공간 밖에 아무것도 쓰지 않는다** — 파일은 전부 작업 공간 안에 깔리고, 지우는 것은 작업 공간 안의 클론 폴더(`probe-harness-krafton/`) 하나뿐이다. 과제 지침의 「파일은 이 안에서만」과 부딪히지 않으니 일부를 빼거나 복사본(`setup.local.sh` 류)을 만들어 돌리지 않는다 — 바꿔 돌리면 출력 맨 끝 지시(설명 탭 안내 · 데이터 서브에이전트 제안 · 세션 등록)가 빠진다. `CODEX_HOME`·`TMP` 같은 환경변수를 바꿔 돌리지 않는다. 세팅 전부터 있던 파일(과제 원본)은 종류와 상관없이 덮지 않고, 과제가 준 `AGENTS.md` 는 우리 `AGENTS.md` 맨 끝 「과제 환경이 준 원래 지침」 절로 옮긴다.
3. setup.sh 출력 맨 끝 **「다음(에이전트)」 지시를 그대로 따른다.** 세팅 뒤 할 일(역할 읽기 · 세션 등록 · 보고 전달 · 덧붙일 안내)의 정본은 그 출력 하나다. 사용자에게 하는 세팅 보고는 줄여 쓰지 않는다 — **보고 ①~④ · 작업 방식 실측 요청(A/B 판정) · 스킬 확인 줄(`$` 에 handoff 가 보이나 — 안 잡히면 `.agents/skills/<이름>/SKILL.md` 를 직접 읽으면 된다고 함께 말한다) · 설명 탭 여는 문장 · `다음 입력(오케): 「과제 시작하자」`** 다섯이 다 들어가야 한다(설명 탭 안내가 빠지면 사용자는 서술형 대비를 시작하지 못한다).
4. **동시 세션(탭) 수 상한**과 서브에이전트가 상한에 포함되는지는 시험마다 다르다 — 「과제 시작하자」 턴의 종료 시각 질문과 함께 사용자에게 묻고 `docs/과제설정.md` 5절에 적는다(`harness/guides/편성.md`).

## 세팅 뒤 작업 공간 모습

```
README.md  EXPORT_SCHEMA.md 류  data/ …   ← 과제 원문 (그대로 — 루트 README 취급은 docs/과제설정.md 2절)
메모.md                    ← 사용자가 직접 만드는 메모장 (에이전트는 읽지 않는다)
사람용-지침.md              ← 사람이 시험 중 보는 한 장(판단 기준 셋 · 3시간 시간표)
Codex-앱-조작.md            ← 사람이 보는 Codex 앱 조작 한 장(단축키 · 실측 4단계 · 우편함 사용법)
AGENTS.md                  ← 모든 탭 공통 규칙
docs/                      ← 과제설정 · PROBLEM · SOLUTION · PLAN · ARCHITECTURE · DECISIONS · 서술형-대비 · 세션.txt · 우편함/(방식 B 의 세션 간 우편 — 커밋 안 함) · interview/
.agents/skills/            ← 스킬 9개 ($handoff $verify $decision $evaluate $design-review $security $submit $grilling $systematic-debugging)
harness/                   ← 에이전트만 본다: roles/ guides/ starter/ tools/ vendor/ pitch/(발표자료 틀 — 사용자가 시킬 때만) verify.sh
```

## 흐름 한 줄

논의하며 진행한다(오케가 단계마다 할 일과 방향을 먼저 꺼내 정하고, 서브에이전트·탭은 제안·승인으로만 늘린다). 세팅(M0) → 「과제 시작하자」(M1 과제설정: 원문 전부 → 과제설정 · PROBLEM 첫판 → 채팅 보고) → 「DM 시작하자」(M1 실무자 대화, DM 탭 — 그동안 화면 골격을 미리 세운다) → 「문제 확정」 → M2 조사 · 솔루션 논의(가장 단순한 안부터) · 솔루션 브리핑 → 「OK」 → 솔루션 DM → 「솔루션 확정」 → M3 설계 논의(화면이 있으면 화면 흐름도 논의) · `$grilling` 빈틈 훑기 · 설계 브리핑 → 「설계 OK」(스캐폴드 · 계약 테스트 · 구현을 누가 어떻게 할지 정하기 — 필요하면 탭 제안) → M4 구현 → 첫 화면 · 사용자 QA · 화면 점검(`$design-review`) · 독립 재계산(둘 다 서브로 돌릴지 제안·승인) → 「구현 끝」「QA 끝」 → M5 피드백 DM · 수정 → 「피드백 끝」(제출 정리) → 점검 기준 고정 → M6 보안·평가·제출 점검(서브에이전트로 돌릴지 제안·승인) → `final` → 서술형 대비 한 바퀴 묻고 답하기 → 제출. 설명 탭은 처음부터 띄워 작업 내내 쓴다. 단계별 상세는 `harness/guides/STAGES/`, 시간 기준선은 `harness/guides/지도.md`(3시간 기준 — 사람용 표는 `사람용-지침.md`).
